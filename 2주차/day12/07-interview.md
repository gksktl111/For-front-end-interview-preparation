면접 질문을 보고 먼저 직접 답한 뒤, 아래 예시 답변과 체크 포인트를 비교한다. 카테고리는 여섯 개로 제한한다.

## 1. 컴포넌트 책임

### React 컴포넌트를 어떤 기준으로 분리하는가?

#### 내 답변

- JSX 줄 수나 재사용 횟수보다 책임과 변경 이유를 기준으로 분리한다. 예를 들어 사용자 편집 폼, 삭제 확인 dialog, 조회 결과 상태가 서로 독립적으로 바뀐다면 각 역할을 별도 컴포넌트로 둘 수 있다. 컴포넌트의 역할을 한 문장으로 설명해 보고, 여러 동등한 역할을 나열해야 한다면 경계를 검토한다.

#### 체크 포인트

- 한 문장 역할
- 서로 다른 변경 이유
- 독립된 UI·State·데이터 의존성
- 파일 길이는 보조 신호

### 컴포넌트가 작을수록 항상 좋은가?

#### 내 답변

- 아니다. 한 화면 안에서 함께 읽어야 하는 작은 State와 JSX를 지나치게 나누면 파일 이동과 Props 연결 비용만 커질 수 있다. 재사용되지 않아도 독립된 책임이 있으면 분리할 가치가 있지만, 단지 div 한 줄을 별도 파일로 옮기는 것은 책임 분리가 아니다. 응집도가 높은 코드는 가까이 두는 편이 좋다.

#### 체크 포인트

- 과도한 파일 분산 비용
- 응집도 우선
- 재사용은 필요조건이 아님
- HTML 구조만 쪼개지 않음

### 하나의 컴포넌트가 너무 많은 책임을 가진다는 것을 어떻게 판단하는가?

#### 내 답변

- query, mutation, form draft, modal, selection, permission, 결과 분기가 한 컴포넌트에 있고 각각 다른 요구사항에 따라 바뀐다면 과도한 책임 신호다. 각 로직이 독립적인 UI 경계인지, 상태 전이인지, 순수 규칙인지 구분한 뒤 컴포넌트·Custom Hook·순수 함수 중 적절한 경계를 선택한다. 단, 학습용 비교 화면처럼 여러 요소가 함께 있어야 목적이 드러나는 경우는 분리하지 않을 수 있다.

#### 체크 포인트

- 변경 이유의 독립성
- State Owner
- UI 경계와 로직 경계 구분
- 목적 있는 예외

## 2. UI 로직과 Custom Hook

### Custom Hook을 만드는 목적은 무엇인가?

#### 내 답변

- Custom Hook은 React Hook을 조합해 상태 전이, Effect, 데이터 요청처럼 UI와 분리할 가치가 있는 로직을 재사용 가능한 계약으로 만드는 함수다. 목적은 단순히 코드 줄 수를 줄이는 것이 아니라 컴포넌트 복잡도를 낮추고, 상태 규칙을 응집시키며, 독립적인 테스트와 재사용을 가능하게 하는 것이다.

#### 체크 포인트

- 상태 로직의 책임 분리
- 재사용 가능한 계약
- 테스트 가능성
- 코드 숨기기와 구분

### 어떤 로직을 Custom Hook으로 분리하는 것이 적절한가?

#### 내 답변

- 복잡한 상태 전이, 여러 Effect, query와 mutation 조합, pagination, selection, form 제어, 외부 API 연동, 권한 상태 조합처럼 하나의 역할로 설명 가능한 React 로직이 적절하다. React를 전혀 사용하지 않는 권한 판정이나 금액 계산은 Hook보다 순수 함수가 더 적합하다. 한 컴포넌트의 짧은 State와 handler는 그대로 두는 편이 더 읽기 쉬울 수 있다.

#### 체크 포인트

- 한 문장으로 설명 가능한 책임
- React Hook 사용 여부
- 순수 함수 우선 사례
- 작은 로직은 추출하지 않음

### Custom Hook을 지나치게 많이 만들면 어떤 문제가 발생할 수 있는가?

#### 내 답변

- 작은 Hook을 무작정 늘리면 호출 흐름이 여러 파일로 흩어지고, 화면의 실제 상태 전이를 이해하려면 너무 많은 구현을 따라가야 한다. 반대로 usePage 하나가 모든 것을 반환하면 God Hook이 된다. Hook의 수를 최적화하는 것이 아니라, 실제 사용자 흐름에 맞는 응집된 책임 단위로 나누는 것이 중요하다.

#### 체크 포인트

- 파일 탐색 비용
- God Hook
- 상태 전이의 응집도
- Hook 개수에 절대 기준 없음

## 3. Hook Rules

### Hook을 조건문에서 호출하면 안 되는 이유는 무엇인가?

#### 내 답변

- React는 렌더링마다 Hook 호출 순서를 기준으로 각 State, Effect, ref를 연결한다. 조건에 따라 useState나 useQuery가 호출되거나 생략되면 다음 Hook의 위치가 달라져 React가 같은 슬롯에 다른 상태를 연결하게 된다. 따라서 조건문뿐 아니라 반복문, event handler, 중첩 함수, 조건부 early return 아래에서도 일반 Hook을 호출하면 안 된다.

#### 체크 포인트

- 렌더마다 같은 호출 순서
- State·Effect 연결
- 조건, loop, nested function
- top level 호출

### Hook 호출 순서가 중요한 이유는 무엇인가?

#### 내 답변

- Hook은 변수 이름이 아니라 컴포넌트 렌더에서 호출된 순서로 상태와 연결된다. 첫 번째 렌더의 첫 번째 useState와 다음 렌더의 첫 번째 useState가 같은 State여야 한다. 순서가 달라지면 State가 밀리거나 Effect 수명이 잘못 연결될 수 있어 React가 오류를 낸다.

#### 체크 포인트

- 순서 기반 연결
- 렌더 간 일관성
- State가 이름으로 연결되는 것이 아님
- 예측 가능한 렌더

### 조건부 데이터 요청은 Hook을 조건부로 호출하지 않고 어떻게 처리하는가?

#### 내 답변

- Hook은 항상 최상위에서 호출하고, userId 같은 입력을 Hook에 전달한다. React Query라면 enabled: Boolean(userId)로 queryFn 실행만 막을 수 있고, Effect 기반 Hook이라면 Effect callback 내부에서 userId가 없을 때 return한다. 즉 Hook 호출은 고정하고 요청·구독·계산 같은 내부 동작만 조건부로 만든다.

#### 체크 포인트

- Hook은 항상 호출
- enabled
- Effect 내부 조건
- 조건부 동작

## 4. Composition과 Props Drilling

### Composition이란 무엇인가?

#### 내 답변

- Composition은 부모가 children, header, sidebar, footer 같은 UI 조각을 Props로 받아 화면을 조합하는 방식이다. 중간 컴포넌트가 user 같은 도메인 데이터를 직접 전달받지 않고, 필요한 Profile UI를 slot으로 배치하게 만들 수 있다. 이로써 레이아웃과 도메인 UI의 결합도를 낮춘다.

#### 체크 포인트

- children과 named slot
- UI 조각 주입
- 레이아웃과 도메인 분리
- Props를 완전히 대체하지 않음

### Props Drilling을 Composition으로 해결할 수 있는 경우는 언제인가?

#### 내 답변

- 중간 컴포넌트가 데이터를 사용하지 않고 단순 전달만 하며, 상위 컴포넌트가 실제로 필요한 하위 UI를 알고 있을 때 적합하다. 예를 들어 Layout이 sidebar를 배치하기만 한다면 user를 Layout과 Sidebar에 전달하는 대신 Profile user UI를 sidebar slot에 넘긴다. 두세 단계의 명시적인 Props 전달은 항상 문제는 아니다.

#### 체크 포인트

- 중간 전달자만 존재
- 상위에서 구체 UI를 만들 수 있음
- Layout의 도메인 의존성 제거
- 깊이만으로 판단하지 않음

### Composition과 Context는 어떤 기준으로 선택하는가?

#### 내 답변

- 하나 또는 소수의 구체적인 UI를 배치하는 문제라면 Composition을 먼저 본다. theme, locale, session, workspace처럼 여러 깊은 하위 컴포넌트가 독립적으로 같은 값을 읽고, 부모가 모든 UI를 slot으로 조합하기 부자연스러우면 Context를 검토한다. Context는 값 전달 기능이지 모든 Props Drilling의 자동 해법이나 전역 상태 관리와 동의어는 아니다.

#### 체크 포인트

- 소비자 수와 독립성
- 공통 인프라 값
- Provider 범위
- Composition 먼저 검토

## 5. 조건부 렌더링과 책임 분리

### 복잡한 조건부 렌더링을 어떻게 개선할 수 있는가?

#### 내 답변

- loading, error, empty, content, mode처럼 화면 결과가 여러 개인 경우 Results 컴포넌트로 분리하고 early return으로 우선순위를 표현한다. 상위 페이지는 query와 event, toolbar를 조합하고 결과 컴포넌트는 화면 상태 정책만 담당하게 된다. 분기 순서는 초기 loading, stale data, error 동시 표시 같은 제품 정책을 먼저 정한 뒤 작성한다.

#### 체크 포인트

- Results 또는 Boundary 컴포넌트
- early return
- 상위의 조합 책임
- 상태 우선순위는 제품 정책

### 중첩 삼항 연산자를 계속 사용하는 것이 문제가 되는 이유는 무엇인가?

#### 내 답변

- 중첩 삼항 자체가 잘못된 문법은 아니지만, 조건이 많아지면 어떤 상태가 먼저인지와 각 branch가 무엇을 보여 주는지 파악하기 어려워진다. 수정할 때 괄호와 조건 순서를 실수하기 쉽고 테스트할 상태도 보이지 않는다. 아주 짧은 두 갈래 분기는 JSX에 두되, 여러 화면 상태가 섞이면 이름 있는 결과 컴포넌트로 옮긴다.

#### 체크 포인트

- 가독성과 우선순위
- 변경·테스트 비용
- 짧은 분기는 허용
- 조건 수가 경계 신호

### 조건을 named variable로 분리하면 어떤 장점이 있는가?

#### 내 답변

- isAdmin, hasSelection, canDelete처럼 이름을 붙이면 boolean 식이 표현하는 도메인 의미가 드러난다. 조건을 수정하거나 false 원인을 디버깅할 때도 세부 규칙을 따로 볼 수 있다. 여러 곳에서 같은 규칙을 쓰면 순수 predicate 함수로 추출해 테스트할 수 있지만, 한 번 쓰는 단순 조건까지 Hook이나 함수로 만들 필요는 없다.

#### 체크 포인트

- 도메인 의미
- 디버깅 가능성
- 순수 predicate 함수
- 과도한 추출 방지

## 6. 설계 판단

### UI 로직과 비즈니스 로직은 반드시 분리해야 하는가?

#### 내 답변

- 반드시 그렇지는 않다. 작은 컴포넌트에서 입력 State와 click handler를 JSX 가까이에 두는 것이 가장 명료할 수 있다. 상태 전이·요청·권한·pagination이 커져 UI를 읽기 어렵게 하거나 독립된 변화 이유가 생길 때만 Custom Hook, 순수 함수, 별도 컴포넌트로 경계를 만든다.

#### 체크 포인트

- 규모와 응집도
- 분리의 비용
- 독립된 변화 이유
- UI 가까이 둘 수 있는 로직

### 재사용되지 않는 컴포넌트도 분리할 가치가 있는가?

#### 내 답변

- 있다. DeleteUserDialog처럼 한 화면 전용이어도 독립된 UI 상태, 접근성, 확인 흐름, 변경 이유를 가진다면 분리할 가치가 있다. 반대로 재사용될 것 같다는 추측만으로 지나치게 범용적인 API를 만들면 현재 화면의 응집도를 잃고 사용하기 어려운 컴포넌트가 된다.

#### 체크 포인트

- 화면 전용 경계도 가능
- 독립된 책임
- 미래 재사용 추측 경계
- 과도한 범용화

### Custom Hook이 너무 많은 값을 반환하면 어떤 설계 문제를 의심할 수 있는가?

#### 내 답변

- selection, pagination, modal, query, mutation, permission, form처럼 여러 도메인의 상태를 하나가 모두 소유하는 God Hook일 수 있다. 반환값을 쓰는 영역이 분리되어 있거나 Hook 이름을 한 문장으로 설명하기 어렵다면 책임이 넓다는 신호다. useClipSelection처럼 상태 전이 단위로 나누고, React와 무관한 규칙은 순수 함수로 빼는 방향을 검토한다.

#### 체크 포인트

- God Hook 신호
- 반환값 소비 위치
- 상태 전이 단위
- 순수 함수와 구분
