## 1. TypeScript는 런타임 검증을 해주는가?

### 내 답변
- 아니다. TypeScript는 런타임 이전, 즉 컴파일 타임에 타입 오류 가능성을 확인해주는 정적 타입 검사 도구다. 타입 정보는 JavaScript로 변환되면 일반적으로 사라지기 때문에 런타임 값이 실제로 안전한지는 자동으로 검증되지 않는다. API 응답, 사용자 입력, 로컬스토리지 값처럼 외부에서 들어오는 데이터는 타입 가드나 검증 라이브러리로 별도 확인해야 한다.

### 체크 포인트

- TypeScript는 컴파일 타임에 동작한다는 점
- 타입 정보는 런타임에 자동 검증되지 않는다는 점
- 외부 입력은 타입 선언만으로 신뢰하면 안 된다는 점
- 런타임 검증은 타입 가드나 검증 라이브러리로 별도 처리해야 한다는 점

---

## 2. `any`와 `unknown`의 차이는 무엇인가?

### 내 답변
- `any`는 어떤 값이든 허용하고, 속성 접근이나 메서드 호출도 대부분 통과시킨다. 그래서 TypeScript의 정적 분석 보호를 사실상 우회하게 되고, 잘못된 접근은 런타임 에러로 이어질 수 있다.
- `unknown`도 어떤 값이든 받을 수 있다는 점은 비슷하지만, 타입을 좁히기 전에는 속성 접근이나 메서드 호출을 허용하지 않는다. 따라서 외부 입력처럼 구조를 확신할 수 없는 값은 `unknown`으로 받은 뒤 타입 가드나 타입 좁히기를 거쳐 사용하는 것이 더 안전하다.

### 체크 포인트

- `any`는 TypeScript의 보호를 우회한다는 점
- `unknown`은 바로 사용할 수 없고 좁히기가 필요하다는 점
- 외부 입력에는 `unknown`이 더 안전하다는 점
- `any`는 필요한 경우에도 범위를 좁게 유지해야 한다는 점

---

## 3. `never`는 언제 사용하는가?

### 내 답변
- `never`는 도달할 수 없는 값의 타입을 표현할 때 사용한다. 실무에서는 유니언 타입의 모든 분기를 처리했는지 검사할 때 자주 쓴다.
- 예를 들어 렌더링 상태가 `idle`, `loading`, `success`, `error`로 나뉘어 있다면 `switch`문에서 모든 상태를 처리하고, `default`에서 `never` 타입을 받는 `assertNever` 함수를 호출하는 패턴을 사용할 수 있다. 나중에 상태가 추가됐는데 분기 처리를 빠뜨리면 컴파일 타임에 타입 오류로 확인할 수 있다.

### 체크 포인트

- `never`는 도달할 수 없는 타입이라는 점
- 빠진 유니언 분기 검사용으로 사용할 수 있다는 점
- `assertNever` 패턴을 설명할 수 있어야 한다는 점
- 상태가 추가될 때 컴파일 타임에 누락을 발견할 수 있다는 점

---

## 4. 유니언 타입을 안전하게 사용하려면 어떻게 해야 하는가?

### 내 답변
- 유니언 타입은 값이 여러 타입 중 하나일 수 있다는 의미이므로, 바로 특정 타입의 속성이나 메서드에 접근하면 안전하지 않다. 먼저 분기 조건을 통해 타입을 좁힌 뒤 사용해야 한다.
- 원시값은 `typeof`로 좁힐 수 있고, 객체 유니언은 `in` 연산자로 특정 프로퍼티가 있는지 확인할 수 있다. 반복되는 검증 로직은 사용자 정의 타입 가드로 분리할 수 있다. 상태처럼 공통 판별 필드가 있는 경우에는 `status`, `type`, `kind` 같은 필드를 기준으로 좁히는 Discriminated Union을 사용하는 것이 좋다.

### 체크 포인트

- 유니언은 여러 가능성 중 하나를 표현한다는 점
- 분기 조건으로 타입을 좁혀야 한다는 점
- `typeof`는 원시 타입 구분에 유용하다는 점
- `in`은 객체 프로퍼티 존재 여부로 좁힐 때 사용할 수 있다는 점
- 반복 검증은 사용자 정의 타입 가드로 분리할 수 있다는 점

---

## 5. Discriminated Union이 왜 유용한가?

### 내 답변
- Discriminated Union은 유니언의 각 타입이 `status`, `type`, `kind` 같은 공통 판별 필드를 가지는 구조다. 이 판별 필드를 기준으로 분기하면 TypeScript가 해당 분기 안에서 타입을 정확히 좁혀준다.
- 예를 들어 API 요청 상태를 `idle`, `loading`, `success`, `error`로 나누고, `success` 상태에만 `data`, `error` 상태에만 `error`를 두면 성공 데이터와 에러가 동시에 존재하는 잘못된 상태를 막을 수 있다. 호출부나 렌더링 코드에서도 `state.status`만 확인하면 상태별로 안전하게 필요한 값에 접근할 수 있다.

### 체크 포인트

- 공통 판별 필드를 가진 유니언이라는 점
- 판별 필드 기준으로 안전하게 타입이 좁혀진다는 점
- 상태별로 필요한 데이터만 들고 있게 할 수 있다는 점
- 불가능한 상태 조합을 줄일 수 있다는 점

---

## 6. 유니언 타입과 인터섹션 타입의 차이는 무엇인가?

### 내 답변
- 유니언 타입은 여러 타입 중 하나일 수 있음을 표현하고, 인터섹션 타입은 여러 타입을 모두 만족해야 함을 표현한다. `A | B`는 A 또는 B이고, `A & B`는 A와 B의 조건을 모두 만족하는 타입이다.
- 상태나 결과처럼 여러 경우 중 하나를 표현할 때는 유니언이 적합하고, 공통 필드나 기능을 조합할 때는 인터섹션이 유용하다.

### 체크 포인트

- 유니언은 "또는"에 가깝다는 점
- 인터섹션은 "모두"에 가깝다는 점
- 상태 모델링에는 유니언이 자주 쓰인다는 점
- 공통 필드 조합에는 인터섹션이 유용할 수 있다는 점

---

## 7. 함수 반환 타입을 명시하면 어떤 장점이 있는가?

### 내 답변
- 함수 반환 타입은 호출부와의 계약을 명확히 해준다. 반환 타입을 명시하면 함수 내부 구현이 바뀌는 과정에서 의도와 다른 값을 반환하는 실수를 TypeScript가 잡아줄 수 있다.
- 특히 API 클라이언트 함수, 상태를 만드는 함수, 성공과 실패를 함께 다루는 함수처럼 외부에서 재사용되거나 분기가 많은 함수는 반환 타입을 명시하는 편이 안전하다. 모든 지역 함수에 무조건 반환 타입을 적기보다, 변경 영향이 큰 경계에 우선 적용하는 것이 좋다.

### 체크 포인트

- 반환 타입은 함수의 외부 계약이라는 점
- 구현 변경 시 잘못된 반환을 잡을 수 있다는 점
- 성공/실패 흐름이 있는 함수에서는 특히 중요하다는 점
- 모든 지역 함수에 무조건 적는 것보다 위험한 경계에 우선 적용한다는 점

---

## 8. 성공과 실패를 반환 타입으로 어떻게 표현할 수 있는가?

### 내 답변
- 성공과 실패를 `ok`나 `status` 같은 판별 필드를 가진 유니언 타입으로 표현할 수 있다. 예를 들어 `{ ok: true; data: T } | { ok: false; error: string }` 같은 Result 타입을 만들면 호출부가 `result.ok`로 분기한 뒤 성공일 때는 `data`, 실패일 때는 `error`에 안전하게 접근할 수 있다.
- 이렇게 설계하면 성공 데이터와 실패 정보가 동시에 존재하는 잘못된 상태를 줄일 수 있고, 실패를 단순히 `null`로 반환하는 것보다 실패 이유도 명확히 전달할 수 있다.

### 체크 포인트

- 성공과 실패를 하나의 일관된 유니언으로 표현한다는 점
- `ok` 필드가 판별자 역할을 한다는 점
- 성공 데이터와 실패 정보가 동시에 존재하는 상태를 막을 수 있다는 점
- 실패 이유를 `null`로 숨기지 않고 명확히 전달할 수 있다는 점

---

## 9. 제네릭은 언제 사용하는가?

### 내 답변
- 제네릭은 타입을 사용하는 시점에 전달해서 입력과 출력의 타입 관계를 유지해야 할 때 사용한다. 같은 로직을 여러 타입에 재사용하면서도 `any`처럼 타입 정보를 잃지 않게 해준다.
- 예를 들어 배열의 첫 번째 요소를 반환하는 함수는 입력 배열의 요소 타입에 따라 반환 타입도 달라져야 한다. 이때 `function first<T>(items: T[]): T | undefined`처럼 제네릭을 사용하면 `string[]`을 넣으면 `string | undefined`, `number[]`를 넣으면 `number | undefined`로 추론된다.
- 다만 타입 관계를 표현하는 이점이 없는데 제네릭을 남발하면 코드가 오히려 복잡해질 수 있다.

### 체크 포인트

- 제네릭은 타입 파라미터라는 점
- 입력과 출력의 타입 관계를 표현한다는 점
- `any` 없이 재사용성을 확보할 수 있다는 점
- 필요 없는 제네릭은 오히려 복잡도를 높일 수 있다는 점

---

## 10. `interface`와 `type`은 어떻게 선택하는가?

### 내 답변
- `interface`와 `type`은 둘 다 객체 타입을 표현할 수 있다. 실무에서는 확장 가능한 객체 모델은 `interface`, 유니언이나 인터섹션, 함수 타입, 튜플, 원시값 조합은 `type`을 우선 고려한다.
- 예를 들어 도메인 객체나 props처럼 객체 형태가 중심이고 확장 가능성이 있으면 `interface`가 자연스럽다. 반면 `status: "idle" | "loading" | "success" | "error"` 같은 상태 유니언이나 Result 타입은 `type`이 더 적합하다. 다만 프로젝트나 팀 컨벤션이 있다면 일관성을 우선하는 것이 좋다.

### 체크 포인트

- 둘 다 객체 타입 표현이 가능하다는 점
- 객체 확장 모델은 `interface`가 자연스럽다는 점
- 유니언과 인터섹션 조합은 `type`이 적합하다는 점
- 팀 컨벤션과 일관성이 중요하다는 점
