# Day 5 Interview Practice

면접 질문을 보고 바로 아래 `내 답변` 칸에 스스로 답변을 적는 용도입니다.

## 1. 브라우저가 HTML을 화면에 표시하는 과정을 설명해달라.

### 내 답변
- 브라우저는 HTML을 파싱해 DOM Tree를 만들고, CSS를 파싱해 CSSOM을 만든다. 그다음 DOM과 CSSOM을 조합해 실제 화면에 그릴 노드와 스타일로 이루어진 Render Tree를 만든다. 이후 Layout 단계에서 각 요소의 크기와 위치를 계산하고, Paint 단계에서 픽셀을 그릴 명령을 만든 뒤, Composite 단계에서 레이어를 합성해 최종 화면을 표시한다.

### 체크 포인트

- HTML 파싱과 DOM 생성
- CSS 파싱과 CSSOM 생성
- DOM과 CSSOM을 조합한 Render Tree
- Layout은 크기와 위치 계산
- Paint는 픽셀로 그릴 내용 생성
- Composite는 레이어 합성

---

## 2. DOM, CSSOM, Render Tree는 어떻게 다른가?

### 내 답변
- DOM은 HTML을 브라우저가 해석해서 만든 문서 구조이고, CSSOM은 CSS 규칙을 해석해서 만든 스타일 규칙 구조다. Render Tree는 DOM과 CSSOM을 조합해 실제 화면에 그릴 노드와 계산된 스타일만 포함한 구조다. 예를 들어 `display: none` 요소는 DOM에는 있지만 화면에 그리지 않기 때문에 Render Tree에는 포함되지 않는다.

### 체크 포인트

- DOM은 HTML 구조라는 점
- CSSOM은 CSS 규칙 구조라는 점
- Render Tree는 실제 렌더링 대상이라는 점
- DOM에 있어도 Render Tree에 없을 수 있다는 점

---

## 3. Layout과 Paint의 차이는 무엇인가?

### 내 답변
- Layout은 요소의 크기와 위치를 계산하는 단계다. `width`, `height`, `padding`, `display`, DOM 추가처럼 배치에 영향을 주는 변경은 Layout을 다시 유발할 수 있다. Paint는 계산된 위치와 크기를 바탕으로 색상, 배경, 테두리, 그림자 같은 픽셀을 그리는 단계다. 색상 변경은 보통 Layout 없이 Paint만 다시 발생할 수 있다.

### 체크 포인트

- Layout은 위치와 크기 계산이라는 점
- Paint는 시각적 픽셀을 그리는 단계라는 점
- 크기나 위치 변경은 Reflow로 이어질 수 있다는 점
- 색상 변경은 주로 Repaint 대상이라는 점

---

## 4. Reflow와 Repaint는 무엇이고 어떤 차이가 있는가?

### 내 답변
- Reflow는 요소의 크기나 위치가 바뀌어 Layout을 다시 계산하는 작업이다. DOM 추가, 요소 크기 변경, 폰트 크기 변경, 줄바꿈 변화 등이 원인이 될 수 있다. Repaint는 레이아웃은 그대로 두고 색상이나 배경처럼 픽셀을 다시 칠하는 작업이다. Reflow가 발생하면 Paint도 이어질 수 있지만, Paint가 발생한다고 항상 Reflow가 필요한 것은 아니다.

### 체크 포인트

- Reflow는 Layout 재계산이라는 점
- Repaint는 픽셀 다시 그리기라는 점
- Reflow가 더 넓은 영향을 줄 수 있다는 점
- 성능 문제는 DevTools Performance 탭으로 확인해야 한다는 점

---

## 5. 시맨틱 HTML이 접근성에 중요한 이유는 무엇인가?

### 내 답변
- 시맨틱 HTML은 요소의 의미와 역할에 맞는 태그를 사용하는 것이다. 의미에 맞는 태그를 쓰면 브라우저가 기본 키보드 동작, 포커스 처리, 폼 동작, 접근성 역할을 제공한다. 예를 들어 실제 `button`은 Tab으로 포커스할 수 있고 Enter와 Space로 실행되며 스크린 리더에 버튼으로 노출된다. 그래서 접근성과 유지보수 관점에서 `div`에 역할을 억지로 붙이는 것보다 기본 HTML 요소를 먼저 사용하는 것이 좋다.

### 체크 포인트

- 시맨틱 HTML은 의미에 맞는 태그 사용이라는 점
- 브라우저 기본 동작을 활용할 수 있다는 점
- 접근성 트리에 올바른 역할이 전달된다는 점
- ARIA보다 기본 HTML 요소를 우선해야 한다는 점

---

## 6. `div role="button"`보다 실제 `button`이 나은 이유는 무엇인가?

### 내 답변
- 실제 `button`은 기본적으로 포커스 가능하고 Enter와 Space 키로 실행되며, 스크린 리더에 버튼 역할로 노출된다. 또한 `disabled`, `type` 같은 기본 속성을 사용할 수 있다. 반면 `div role="button"`은 역할 이름만 보완할 뿐 실제 버튼의 키보드 동작이나 비활성화 동작을 자동으로 제공하지 않으므로 직접 구현해야 할 것이 많고 실수하기 쉽다.

### 체크 포인트

- `button`은 기본 키보드 접근성을 제공한다는 점
- `role`은 의미 보완이지 동작 구현이 아니라는 점
- 비활성화와 폼 동작 같은 기본 속성을 활용할 수 있다는 점
- 기본 HTML 요소를 먼저 선택해야 한다는 점

---

## 7. `button`과 `a`는 어떻게 구분해서 사용하는가?

### 내 답변
- 현재 화면에서 어떤 동작을 실행하면 `button`을 사용하고, 다른 URL이나 페이지 내 위치로 이동하면 `a`를 사용한다. 예를 들어 저장, 삭제, 복사, 모달 열기는 `button`이 적합하고, 상세 페이지 이동이나 외부 링크 이동은 `a href`가 적합하다. `a href="#"`에 클릭 이벤트만 붙여 버튼처럼 쓰는 방식은 의미와 기본 동작이 어긋나므로 피하는 것이 좋다.

### 체크 포인트

- 액션은 `button`
- 이동은 `a`
- 링크에는 유효한 `href`가 있어야 한다는 점
- 요소의 의미와 사용자 기대 동작을 맞춰야 한다는 점

---

## 8. `async`와 `defer`는 어떻게 다른가?

### 내 답변
- `async`와 `defer`는 모두 스크립트를 다운로드하는 동안 HTML 파싱을 막지 않는다. 차이는 실행 시점과 순서다. `defer`는 DOM 파싱이 끝난 뒤 문서에 선언된 순서대로 실행된다. 반면 `async`는 다운로드가 끝나는 즉시 실행되며 실행 순서가 보장되지 않는다. DOM에 의존하거나 순서가 중요한 앱 코드는 보통 `defer`가 적합하고, 독립적인 분석 스크립트는 `async`가 적합하다.

### 체크 포인트

- 둘 다 다운로드 중에는 HTML 파싱을 막지 않는다는 점
- `defer`는 DOM 파싱 완료 후 순서대로 실행된다는 점
- `async`는 다운로드 완료 즉시 실행된다는 점
- `async`는 실행 순서가 보장되지 않는다는 점

---

## 9. CSS가 렌더링을 막을 수 있는 이유는 무엇인가?

### 내 답변
- 브라우저가 정확한 화면을 그리려면 DOM뿐 아니라 CSSOM도 필요하다. CSS가 아직 준비되지 않으면 요소의 색상, 크기, display 여부 같은 최종 스타일을 알 수 없기 때문에 Render Tree를 만들거나 첫 렌더링을 진행하는 과정이 지연될 수 있다. 그래서 큰 CSS 파일이나 사용하지 않는 CSS가 많으면 초기 렌더링이 늦어질 수 있다.

### 체크 포인트

- CSSOM이 Render Tree 생성에 필요하다는 점
- 최종 스타일을 알아야 정확히 그릴 수 있다는 점
- CSS 파일 크기와 위치가 초기 렌더링에 영향을 줄 수 있다는 점
- 사용하지 않는 CSS를 줄이는 것이 중요하다는 점

---

## 10. Main Thread가 긴 JavaScript Task로 막히면 어떤 문제가 생기는가?

### 내 답변
- Main Thread는 JavaScript 실행, 이벤트 핸들러, 스타일 계산, Layout, Paint 준비, 사용자 입력 처리를 담당한다. 긴 JavaScript 작업이 Main Thread를 오래 점유하면 브라우저가 클릭, 스크롤, 렌더링 같은 작업을 제때 처리하지 못한다. 그래서 버튼 반응이 늦어지고 애니메이션이 끊기며 화면 업데이트가 멈춘 것처럼 보일 수 있다.

### 체크 포인트

- Main Thread가 JS 실행과 렌더링 관련 작업을 처리한다는 점
- 긴 Task는 사용자 입력 처리를 지연시킨다는 점
- 렌더링과 애니메이션이 끊길 수 있다는 점
- 작업을 나누거나 Web Worker를 검토할 수 있다는 점

---

## 11. `z-index`가 예상대로 동작하지 않을 때 무엇을 확인해야 하는가?

### 내 답변
- `z-index`는 모든 요소가 전역적으로 숫자만 비교하는 방식이 아니라 같은 stacking context 안에서 비교된다. 따라서 숫자가 큰데도 위로 올라오지 않는다면 부모 요소가 `transform`, `opacity`, `position`과 `z-index` 등으로 새로운 stacking context를 만들고 있는지 확인해야 한다. 또한 비교 대상들이 같은 stacking context 안에 있는지, 불필요한 `position`이나 `z-index`가 쌓여 있지는 않은지 확인해야 한다.

### 체크 포인트

- `z-index`는 같은 stacking context 안에서 비교된다는 점
- 부모의 `transform`, `opacity`, `z-index`가 영향을 줄 수 있다는 점
- 단순히 숫자를 키우는 것이 근본 해결이 아닐 수 있다는 점
- DOM 구조와 stacking context를 함께 봐야 한다는 점

---

## 12. `label`이 입력 요소와 연결되어야 하는 이유는 무엇인가?

### 내 답변
- `label`이 입력 요소와 연결되면 사용자가 라벨을 클릭했을 때 해당 입력에 포커스가 이동하고, 스크린 리더가 입력의 목적을 읽을 수 있다. React에서는 `label`의 `htmlFor`와 `input`의 `id`를 맞춰 연결한다. 화면상으로 텍스트가 input 옆에 있어도 DOM상 연결이 없으면 보조 기술이 입력의 의미를 파악하기 어렵다.

### 체크 포인트

- 라벨 클릭으로 입력 포커스가 가능하다는 점
- 입력 요소의 accessible name을 제공한다는 점
- React에서는 `htmlFor`를 사용한다는 점
- 시각적 근접성과 의미 연결은 다르다는 점
